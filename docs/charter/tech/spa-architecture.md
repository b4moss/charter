# SPAの開発について

バックエンドとフロントエンドを分けたいわゆる **SPA構成** の開発をする場合、以下の原則で設計します。

## 設計はDTOから始める

必須ではありませんが、[薄いDDD](./thin-ddd.md)を取る以上、1ユースケースが1APIエンドポイントと考えます(RESTの場合)。

そこで、各ユースケース=エンドポイントごとに、リクエストとレスポンスの型を **JSON Schema** で縛ることを推奨します。

## Swaggerドキュメントを必ず作る

エンドポイントとリクエスト・レスポンスの型が決まったら、Swaggerドキュメントを作ります。

## 各エンドポイントに名前をつける

JSON Schema 作成の段階からでもいいので、名前をつけます。

例: `user.auth.login`, `article.create`, `tag.delete`など

## フロントエンドでは、API Clientを作る

フロントエンドの各コンポーネントから都度fetchするのではなく、薄いAPI Clientを作ってください。
混同してはいけないのが、SDKではないということです。
レスポンスをユースケースごとにどう見せるか、扱うかは、利用側の責務です。
また、API Clientがfetchするのはパスではなく、Swaggerドキュメントに記載された、**エンドポイントの名称** で呼び出します。
そのため、バックエンドが出力したSwaggerドキュメントを何らかの方法で読み込んで、名称とパスを解決してください。
その手法はプロダクトごとに任せます。

- ビルド時にバックエンドからフロントエンドにSwaggerドキュメントを注入する
- バックエンドから、Swaggerドキュメントを配信するエンドポイントを用意する(認証に注意)

また、ユーザー認証が必要なリクエストも、API Clientに載せ、毎回再実装しないようにします。
